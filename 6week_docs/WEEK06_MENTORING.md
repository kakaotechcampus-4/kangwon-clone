# Week 6 멘토링 정리 + 이번 과제 적용 구상 (리뷰어 junho85, 2차 승인)

2차 리뷰 **승인**. 날짜 범위 버그 해소·추가과제 정상 동작 확인. 아래는 멘토가 남겨준 이야기를 정리하고, 이번 과제에 무엇을 적용하면 좋을지 구상한 것.

## 1. AI 의존 방향에 대해

- **"코드 이해 vs 좋은 기능"은 대립이 아니다.** 검증·하네스를 조이는 방향은 맞음.
- 다만 **하네스가 잡는 범위 밖은 본인이 읽어서 판단**해야 한다. 1차 날짜 범위 버그가 checks를 다 통과한 채 남아 있던 게 그 예 — **기준에 없으면 검증되지 않는다.**
- **공부 단계에선 코드 직접 이해 자체가 중요.** "어디를 반드시 읽어야 하는지 고르는 감각"도 결국 직접 읽어본 양에서 나온다. 이해를 포기하는 게 아니라 "어디를 반드시 읽을지 고르는 감각"으로 옮겨가는 것.

## 2. 로그 노하우 (멘토 경험 기준)

1. **어디에 남길지 — 외부 시스템 경계를 먼저.** 넉넉히 남기되 우선순위는 **외부와 만나는 경계**(이번 과제라면 MCP 호출에 넘긴 인자와 받은 응답). 내 코드 안 문제는 읽어서 추적 가능하지만, 경계 밖 일은 그때 기록이 없으면 나중에 알 방법이 없다. 안쪽 중간값까지 같은 밀도로 찍으면 양에 묻혀 필요한 줄을 못 찾음 → 로그 레벨 분리(평소 경계만, 파고들 때 안쪽).
2. **목적은 재현.** 그 줄만 보고 같은 상황을 다시 만들 수 있어야. **사용자 입력 원문 + 도구에 넘긴 인자 + 응답 건수**가 한 세트. "조회 실패"만 찍히면 무엇을 조회했는지 몰라 재현 불가.
3. **요청당 식별자로 흐름 묶기.** `request_id`/`conversation_id`를 로그마다 남기면 여러 도구를 거친 한 요청을 처음부터 끝까지 추적. 로그가 여러 요청과 섞일 때 가장 큰 차이.
4. **실패를 조용히 삼키지 않기.** 외부 호출 실패와 결과가 정말 없는 것이 같은 모양이면 원인 못 가림. **이번 wrapper들이 실패 vs 빈 결과를 구분하는지 점검.**
5. **토큰·개인정보는 로그에 남기지 않기.** 실무에선 사고로 이어짐.

> **이미 하고 있는 것**: Agent Trace가 사실 이 목적의 로그다(어떤 도구가 어떤 인자로 불렸고 뭘 돌려줬는지). 별도 로그를 새로 만들기보다 **trace에서 무엇을 꺼내 남길지 고르는** 쪽이 이번 과제엔 더 빠름.

## 3. 실무: 로그를 어디에 모으나
- 서버가 여러 대·배포가 여러 번이면 파일/콘솔을 사람이 뒤지는 방식은 오래 못 감 → **Sentry 같은 에러 트래킹**.
- 가장 큰 차이: **같은 예외를 하나로 묶어줌**(만 번 나도 항목 1개, 발생 횟수/최초 시각/어느 배포부터). 예외 직전 맥락 자동 첨부(재현 정보를 도구가 모아줌).
- **AI 에이전트 모니터링**: 에이전트 실행·도구 호출·모델 호출·토큰 사용량 수집, 지난 대화·도구 호출을 되짚기. MCP 서버 모니터링 포함. → Agent Trace를 여는 작업이 결국 이 도구가 하는 일. (https://docs.sentry.io/product/insights/agents/)

## 4. 알람을 메신저로
- webhook(슬랙/디스코드 incoming webhook, 텔레그램 봇 API)로 요청 한 번. 야간 호출 단계까지면 PagerDuty/Opsgenie.
- **어려운 건 붙이기가 아니라 "무엇을 보낼지".** 알림이 많으면 아무도 안 봄 → ① 사용자에게 영향 간 것만 ② 반복은 묶어서 한 번. 알림 메시지에도 재현 정보.
- 연습: **MCP 호출 실패 지점에 webhook 한 줄**만 붙여봐도 감 잡힘.

## 5. 애초에 못 만들게 막는 층 (예방)
- **로그/알람 = 사후에 찾기, 하네스 = 미리 재보기, 예방 = 애초에 못 만들게.**
- 이미 쓰는 예: **Pydantic** — `kind`를 `Literal`로 좁히면 스키마 단계에서 걸리고 validator로 한 번 더. 나중에 찾는 것보다 애초에 못 들어오게 하는 게 언제나 더 쌈.
- 언어 차원까지 민 예: **Rust**(메모리 안전을 컴파일 단계에서). 사고방식을 보려고 읽어볼 만함.
- **정리 = 3층**: (1) 못 만들게 막고 → (2) 미리 재보고 → (3) 새는 것 로그로 찾기. 지금 하네스에 힘을 많이 쓰고 있으니 **1층(예방)도 같이** 보면 좋음.

## 6. 서브에이전트 토큰 비용 (6주차 직접 연관)
- 멀티에이전트 구성은 단순 대화보다 **대략 15배 토큰**. 성능은 오르지만 비용도 같이.
- 기준: **전부 쪼개지 말고, 독립된 컨텍스트가 꼭 필요한 곳만 쪼갠다.**

## 7. 이번 과제 적용 구상 (우선순위)

멘토의 3층(예방 → 하네스 → 로그)에 맞춰, 이번 week6 코드에 적용할 것을 정리. (범위: `student_parts/week05·week06` + `checks/`만. `fixed/`는 안 건드림.)

### A. 예방 층 (가장 싸다 — 먼저)
- [ ] **Pydantic 조이기**: week5/6 Input 스키마에서 날짜는 `YYYY-MM-DD` 형식 validator, 시간은 `HH:MM` 형식 validator를 추가해 잘못된 값이 tool 본문에 도달하기 전에 차단. (지금은 문자열만 받음 → 형식 오류가 런타임까지 감)
- 근거: 1차 날짜 범위 버그도 "범위 밖 값이 들어와도 통과"였음. 형식·범위를 스키마에서 막으면 그 부류가 사라짐.

### B. 하네스 층 (기준=스펙, 멘토 핵심)
- [ ] **checks에 "실패 vs 빈 결과 구분" 케이스 추가**: MCP 호출이 실패했을 때와 결과가 0건일 때가 다른 모양으로 반환되는지 계약화. (멘토 로그 원칙 4를 하네스로)
- [ ] (이미 함) 날짜 범위 밖 제외, 후보 겹침 제외 등은 5·6주차 하네스에 있음 — 유지.

### C. 로그 층 (경계 우선 + 재현 + 식별자)
- [ ] **MCP 경계 로깅**: week5/6의 MCP wrapper(`call_mcp_tool_sync`/`call_external_tool_payload` 호출부)에 **넘긴 인자 + 응답 건수 + conversation_id**를 한 줄로 남김. 실패 시엔 실패로 명확히(빈 결과와 구분). 단 **토큰/개인정보 제외**, 응답은 "건수"만(원문 덤프 X).
- [ ] **Agent Trace 활용**: 별도 로그 대신 trace에서 tool_call 인자·tool_result 건수를 뽑아 남기는 쪽으로. (멘토: trace가 이미 그 목적의 로그)
- [ ] (학습용, 선택) **MCP 실패 지점에 webhook 한 줄** 연습 — 실제 알림 붙이는 감 잡기. 무엇을 보낼지(사용자 영향+묶기)를 먼저 정하고.

### D. 아키텍처 판단 기록 (멀티에이전트 비용)
- [ ] **왜 Nana/Kana 둘로만 쪼갰는지** 문서화: "개인 컨텍스트(내 저장소·RAG)"와 "외부 컨텍스트(외부 멤버·MCP)"가 독립적이라 둘로 나눔. 그 이상 잘게 안 쪼갠 이유 = 토큰 ~15배 비용. (독립 컨텍스트 필요한 곳만 분리 원칙)

### 적용 우선순위 제안
1. **A(예방) + B(실패/빈결과 하네스)** — 싸고 효과 큼, 코드 품질 직접 향상. 다음 PR 후보.
2. **C(경계 로깅, trace 활용)** — 중간. 토큰/PII 주의.
3. **webhook·Sentry** — 학습·실무 감각용. 이번 과제 필수는 아님.

> 다음 단계로 A/B부터 실제 구현(예: Input 스키마 날짜 validator + checks "실패 vs 빈결과" 케이스)을 하면, 멘토의 "예방 → 하네스" 두 층을 이번 코드에 바로 얹을 수 있음.
