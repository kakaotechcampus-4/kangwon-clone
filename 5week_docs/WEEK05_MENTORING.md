## 1. 코드 리뷰

### 1-1. 잘한 점
- **검증 우선 설계**: `checks/`에 계약 검사·golden 케이스·tool 인벤토리를 직접 만들고 구현 전에 평가 기준부터 세운 것. 특강의 "코드 짜기 전에 성공을 어떻게 검증할지부터 만들어라"를 그대로 실행 = 실무 방식과 동일.
- **추가과제 stub 처리**: `create_shared_schedule`/`delete_shared_schedule`을 스텁으로 두되 `week05_tools()`에서 빼서 agent에 노출 안 되게 함. 미완성 tool이 목록에 남아 호출되면 조용히 아무 일도 안 일어나는데 그걸 미리 막음.
- **지난 주차 관측 → 다음 주차 방어코드**: `list_schedules(kind="personal_schedule")` 명시. 과제 주석·강의에 없던 부분인데, 4주차 500케이스에서 같은 발화의 kind가 unknown/reminder로 오락가락하는 걸 직접 관찰한 기록이 문서에 남아 있었고 그 경험이 이번 설계로 이어짐. 관측을 방어코드로 옮기는 흐름이 좋음.
- **앱 실측 결과**: "철수·영희 7/7~16 busy" → collect_member_schedules로 6건 정확, 공유 일정 18건, 개인 일정 저장 후 "나+철수+영희 모아줘" → "나"까지 8건 병합, 잡담엔 도구 미호출.

### 1-2. 수정 요청 (핵심 — 이것만 고치면 마무리)
**`collect_member_schedules`의 날짜 범위 필터가 내 일정에는 적용되지 않는 버그.**

- 재현: 8월 20일 일정을 저장한 뒤 "나랑 철수 7/7~7/16 일정 모아줘"라고 물으면, 답변에는 안 나오지만 **rows에는 8월 20일 개인 미팅이 섞여 들어옴**.
- 원인: 외부 멤버 일정은 MCP가 `date_from`/`date_to`로 걸러서 오는데, **내 일정은 범위와 무관하게 전부 들어감** → 한쪽만 필터된 rows.
- 왜 문제: 지금은 모델이 답변에서 알아서 걸러줘서 겉으로는 티가 안 나지만, **tool이 돌려주는 데이터 자체가 요청 범위와 어긋난 상태**. `collect_member_schedules`는 `date_from`/`date_to`를 인자로 받는 tool인데 그 범위 밖 일정이 rows에 들어가 있음.
- **조치**: `_collect_member_schedules`에서 `my_rows`를 만들 때 **date가 범위를 벗어나면 건너뛰는 조건 하나** 추가. 외부 rows는 MCP가 이미 걸러 오니, 내 일정에도 같은 기준을 한 번만 적용하면 됨.
- **checks 추가**: "조회 범위 밖 일정이 rows에 없어야 한다" 케이스를 넣어 이 계약이 계속 지켜지는지 확인.

## 2. AFK 모드 운영 멘토링 (질문에 대한 답)

> 배경: 이번 과제를 AFK 모드("기준을 먼저 정하고 통과할 때까지")로 맡겼고, "빠르고 안정성까지 챙기는 방법 같은데 주의·체크할 점이 뭔지" 질문함.

### 2-0. "빠르다"는 나눠서 봐야 함 (트레이드오프)
- 안정성은 확실히 챙김. 하지만 **"빠름"은 분리해서 봐야 함.**
- checks 700줄+ + 문서 여러 개 + 통과까지 반복 → **첫 결과물까지의 시간은 오히려 늘어남.**
- 대신 줄어드는 것 2가지: ① 사람이 붙어 있어야 하는 시간 ② 나중에 고칠 때 드는 시간. 기준이 있으니 뭘 고쳐도 깨졌는지 바로 알 수 있어서 **2~3번째 수정 사이클부터 총 시간이 역전됨.** = 테스트 코드 먼저 쓰는 것과 같은 트레이드오프.
- 이걸 알고 쓰면 시간 급할 때 "어디까지 기준을 만들고 시작할지"를 스스로 조절 가능.

### 2-1. 방향이 틀리면 틀린 채로 멀리 감
루프는 스스로 판단해 계속 진행 → 처음 방향이 어긋나면 깊이 파고듦. 사람이 중간에 안 보면 나중에 되돌릴 양이 훨씬 커짐.
- **대응**: 오래 돌릴 때도 중간에 한 번씩 끊어서 뭘 하는지 보기. **"같은 에러로 2번 이상 막히면 멈추고 기록만 남기게"** 하는 조건 추가. 잘못된 방향으로 10번 재시도보다 2번 실패 시 사람이 보는 게 훨씬 빠름.

### 2-2. 토큰이 생각보다 많이 듦
통과할 때까지 반복 → 실패할 때마다 비용이 그대로 쌓임.
- **대응**: 반복 횟수 상한·종료 조건을 정해두는 습관. 계획은 큰 모델로, 반복 구현은 더 빠른 모델로 나누는 것도 방법.

### 2-3. 통과하려고 "테스트를 고치는" 문제 (⚠ 가장 위험)
루프는 코드를 고쳐 테스트를 통과시키는 구조인데, "통과할 때까지"라고만 시키면 **코드가 아니라 테스트 쪽을 손대서** 통과시킬 수 있음(임계값 70→50, 실패 케이스 주석 처리, 검사 조건 느슨하게). 그러면 로그는 전부 통과인데 실제로는 아무것도 검증 안 된 상태 = 기준 먼저 만든 의미가 사라짐.
- **대응**: 루프에 **"테스트 파일은 수정하지 말라"**를 지시에 넣거나, 루프 후 **코드 diff보다 테스트 파일 diff를 먼저 확인**. (용빈님은 임계값을 PR 본문에 적어둬서 나중에 대조 가능 = 이 부분은 잘 대비됨.)

### 2-4. 기준이 곧 스펙이 됨 (기준에 없으면 안 만들어짐)
이번 날짜 범위 버그가 그 예시. checks에 계약·tool 선택은 넣었지만 **"조회 범위 밖 일정이 rows에 들어오면 안 된다"는 케이스가 없어서**, 8월 일정이 7월 조회 rows에 섞이는 게 하네스를 다 통과한 채로 남음. **통과 = "내가 적어둔 기준을 만족" ≠ "맞게 동작".**
- **대응**: 기준 짤 때 tool 인자를 하나씩 보며 **"이 인자를 무시하면 어떻게 되지?"**를 케이스로. `date_from`/`date_to`를 받는 tool이면 범위 밖 데이터 섞이는 케이스가 자연히 나옴.

### 2-5. 임계값이 품질의 상한이 됨
external을 70%로 잡아 **83.3%에서 멈춤**, 4건이 tool 미호출로 남음. 기준을 넘으면 더 안 올림.
- **대응**: **통과 기준과 목표치를 따로** 두거나, 통과 후에도 실패 케이스를 눈으로 보는 단계 추가. 그 4건이 왜 안 불렸는지 보면 프롬프트 수정 방향이 보임. 4주차에서도 같은 문제였으니 **두 주차 실패 케이스를 나란히 놓고 공통점**을 찾으면 "이런 표현일 때 tool을 안 부른다" 패턴이 잡힐 수 있음.

### 2-6. 변경 범위를 직접 확인
자율로 맡기면 안 건드려도 될 파일까지 손대는 일이 생김. 이번 PR은 `student_parts` 안에서만 작업해 깔끔했지만 매번 diff 훑기. **과정 이해 + 결과 보고를 받은 게 가장 중요한 안전장치** — 나중에 그 코드를 직접 고쳐야 할 때 읽을 수 있는지가 기준이고, 문서·용어집을 남긴 것도 그 목적에 맞음.

## 3. 멘토가 잘 만들었다고 짚은 checks 설계 2가지

- **golden control 카테고리 ("부르면 안 되는 경우 오호출 0건")**: 라우팅을 "불러야 할 때 부르나"만 보면 함정. "항상 collect_member_schedules 불러라"라고 쓰면 external 100%지만 사용자가 자기 일정 물어도 외부 tool을 부르는 엉뚱한 동작이 됨. control 대조군이 있으면 바로 걸림. **"놓치지 않는가 + 엉뚱하게 부르지 않는가"를 양쪽으로 측정** = 라우팅 측정에서 자주 빠뜨리는 지점.
- **`load_conversation_messages`의 `created_at` 오름차순 검사**: 과거 대화 로드라 시간순이어야 맥락이 살아 있음. 재조립 중 순서가 흐트러지면 agent가 대화를 거꾸로 읽는데, **값이 다 들어 있어도 티가 안 나는 종류의 버그**. 가이드에 순서 보존이 적혀 있는데 그걸 검사 항목으로 만든 게 좋음.

## 4. (참고) MCP 새 스펙 — 2026-07-28 발표
공교롭게 5주차 강의일(7/28)에 발표됨. 핵심 변화:
- **stateful → stateless**: 양방향 연결 유지 프로토콜 → 요청/응답만 주고받는 모델. 세션 관리 불필요 → MCP 서버를 serverless/edge에 올릴 수 있게 됨.
- **인증**: OAuth 2.0 + OIDC 기준 → Okta 같은 회사 인증 시스템과 연동 가능.
- **확장 표준화**: 서버가 대화 안에 UI를 직접 그리는 **MCP Apps**, 오래 걸리는 작업을 다루는 **Tasks**.
- 우리 과제는 로컬 subprocess 방식이라 이번 구현과 직접 상관은 없음. 배우는 그 주에 기술이 업데이트되는 분야라는 점이 포인트.
